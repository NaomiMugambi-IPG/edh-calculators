What this tool is
The EDH Delivery Estimator is a facilitated estimation session tool. It is designed to be used by a PM or BA while running a live session with the delivery teams — Data Engineering, DevOps, Security, Governance, Semantic Modeler, BI, and QA.
You select the delivery scenario, answer team questions, and the tool scores the complexity and produces a validated estimate — total calendar days, sprint count, team effort, and FTE.
When to use it
Use this calculator when you are running a formal estimation session with the delivery teams present. It is most valuable when: the project is Medium size or larger; the project type is a migration, incident, change request, API delivery, or another non-standard scenario; or you need to surface specific team risks and dependencies — not just a day count.
This tool is not a solo exercise. The questions are designed to be asked to each team in a session. Filling in the answers without the relevant team present will produce an unreliable estimate.
How the scoring works
Each question carries a complexity weight. Yes answers add to the total complexity score. The score maps to a t-shirt size, and the size combined with your scenario produces the estimate from the pre-calibrated engine.
0–4 = XS 5–8 = S 9–13 = M 14–19 = L 20+ = XL
MAX() logic: After the requirements phase, all delivery teams work in parallel. Calendar duration equals the longest workstream — not the sum of all workstreams. This is why a project with six active teams does not take six times as long.
Step-by-step guide
1
Project intake (before the session)Fill in the project number, name, intake date, and requester. Do this before the teams join — it is housekeeping, not estimation.
2
Select the scenario (before the session)Choose the scenario that best describes this project. Read the description carefully. If unsure between two, pick the closest and note the caveat. The scenario controls which team questions are shown.
3
Session opener — full roomBefore team questions, ask everyone: (1) Does the scenario look right? (2) Has anyone done something similar before? (3) What is the single biggest unknown that could change the estimate? These catch misalignments before scoring begins.
4
Team questions — one team at a timeWork through each team section. Click the team header to expand. Ask each question to the relevant team and record their answer. The italicised explanation under each question gives context for why you are asking — read it aloud if the team asks why.
5
Watch the live complexity scoreThe bar at the top of Step 3 updates as you record answers. If the size feels wrong based on the room's conversation, check which Yes answers are driving the score — those are the complexity signals.
6
Session close — full roomAfter all sections: (1) Does anything change now that everyone has heard all workstreams? (2) What is your confidence level? (3) Does any team need something from another team before they can start? These surface revisions that only emerge when teams hear each other.
7
Calculate the estimateClick Calculate. Review the output with the teams present before closing. Give teams a chance to flag anything that looks wrong before the number leaves the room.
Facilitator notes
Do not ask for a day count first. Ask the questions, let complexity surface, then ask for a number. Teams that score complexity first give more accurate estimates than teams who anchor on a number and work backwards.
Low confidence = add a buffer or a spike sprint. If any team says their confidence is low, add 20–30% to that workstream or plan a spike sprint before committing the estimate.
Standard delivery scenarios (S1–S6)
Use these for forward-build delivery where you know the source, target, and scope. The scenario is determined by where the data starts and where it needs to go.
S1 — New ingestion → Gold/Semantic
Files or APIs received from client. Ingestion pipelines land data and move it to Gold and/or Semantic (Redshift).
S2 — Bronze → Silver → Gold
Data already in EDH Bronze. Work is transformation and layer movement only — no new source connections.
S3 — Gold → Semantic
Curated Gold data modelled into agreed Semantic / Redshift structures (grain, joins, conformed dimensions).
S4 — Redshift → Dashboards
Data already modelled. Focus is BI dataset and dashboard build plus validation — no pipeline work.
S5 — Hybrid A (Light)
Some EDH data exists; minimal reconciliation; limited ingestion and transformations.
S6 — Hybrid B (Heavy)
New and existing EDH data. Reconciliation, governance review, semantic alignment, downstream impact analysis all required.
Additional delivery scenarios (G1–G7)
Use these when the project does not fit the standard forward-build pattern.
G1 — Migration / cutover
Moving an existing data product from a legacy platform into EDH. Requires parallel-run validation, cutover, and rollback planning.
G2 — Break-fix / incident
Something in production is broken. Investigate → root-cause → fix → validate. Scope is unknown at the start.
G3 — Change request
Client requests a change to something already in production. Starts with impact assessment, then regression testing.
G4 — Multi-source consolidation
Three or more source systems consolidated into a single data product. Size is driven by source count, not complexity score.
G5 — Self-service enablement
Provisioning existing EDH data so a business team can access it themselves. No pipeline build — access and capability only.
G6 — DQ / governance remediation
Fixing known data quality issues, implementing missing DQ rules, or carrying out a commissioned data audit.
G7 — API delivery
The downstream consumer is an application expecting a JSON API. Replaces semantic modelling with API contract design and BI build with endpoint development.
Pre-delivery holds (EC1, EC2)
Use these when delivery cannot start yet. They produce a hold duration estimate — not a delivery estimate. Once the hold resolves, run the estimator again with the appropriate delivery scenario.
EC1 — Requirements unknown
The client cannot confirm what data attributes or schema they need. Held until a signed requirements document is in place.
EC2 — Architecture undecided
The data is known but the downstream architecture is not yet agreed. Held until an Architecture Decision Record (ADR) is approved.
EC1 and EC2 estimate the hold — not the delivery. When the hold resolves, open a new estimate using the appropriate delivery scenario to get the actual project timeline.
Understanding the results
Total calendar days
Days from project kick-off to go-live. Includes waiting time (client responses, approval cycles) — not just build time.
Sprints
Calendar days ÷ 10, rounded up. One sprint = 10 calendar days (2 working weeks).
Internal person-days
Total effort from all internal delivery teams combined. Used for capacity planning. If three teams each spend 10 days, that is 30 person-days — regardless of calendar duration.
Client person-days
Effort required from the client side — clarifications, UAT, data provision, approvals. This is the cost of the project to the client's own team.
Avg internal FTE
Internal person-days ÷ total calendar days. How many delivery team members are working in parallel on average. Use this for sprint staffing decisions.
Team effort bar chart
Shows how person-days split across delivery teams for this scenario at this size. The percentages reflect the scenario's team composition — a dashboard-only project allocates more to BI; a migration allocates more to DevOps and QA.
EDH data layers
Bronze
Raw data landing zone — ingested as received, no transformation.
Silver
Cleansed and standardised data — data types normalised, nulls handled, basic rules applied.
Gold
Business-ready curated data — joins, aggregations, derived fields, full business logic applied.
Semantic / Redshift
Modelled structures in Amazon Redshift designed for analytics and reporting. What BI tools query directly.
Conformed dimension
A shared dimension table (e.g. Date, Employee) used across multiple data products. Changes affect all consumers — not just the current project.
Estimation terms
T-shirt size
Relative size label (XS to XL) assigned from the complexity score. Maps to pre-calibrated workstream day values.
Sprint
A fixed 10-calendar-day period (2 working weeks). Standard time unit in both calculators.
MAX() logic
After requirements, teams work in parallel. Calendar duration = the longest workstream (MAX), not the sum of all workstreams (SUM).
Client TAT
Client Turnaround Time — how long the client takes to respond to a clarification or approve a deliverable. Multiplied by the number of cycles to give total waiting time.
ADR
Architecture Decision Record — a formal document that records the agreed architecture approach. Required to exit an EC2 hold.
ARB
Architecture Review Board — the governance body that approves ADRs. Meets on a fixed schedule; submissions cannot be fast-tracked.
Team abbreviations
BA / PO
Business Analyst / Product Owner — requirements, mapping, user stories, UAT.
Data Eng
Data Engineering — ingestion pipelines, transformations, layer movement.
DevOps
DevOps / Platform — CI/CD, environment provisioning, infrastructure, releases.
DataOps
Pipeline orchestration, monitoring, and SLA alerting — tracked separately from DevOps.

Data Steward / Governance — classification, lineage, retention, metadata, approvals.
