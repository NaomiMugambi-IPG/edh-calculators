What this tool is
The High-Level Estimation Calculator is a pre-consultation sizing tool. It lets you produce an initial project estimate — calendar days, sprints, team effort, and FTE — before you have spoken to any delivery team.
You fill in a short intake form, answer 13 scope questions, and the calculator produces a t-shirt-sized estimate automatically. No Engineering, DevOps, Governance, or BI input is needed.
When to use it
Use this calculator when you need to: give a client or stakeholder a rough timeline before any team is consulted; decide whether a project warrants a full estimation session; or size a backlog of incoming requests for portfolio planning.
Do not use this as the final committed estimate for L or XL projects. At those sizes, the EDH Delivery Estimator with team input is required to validate the output before committing to a date.
How the scoring works
You answer 13 Yes / No questions about the project's scope. Each Yes adds 1 point to the complexity score. The score maps to a t-shirt size, and the size combined with your selected scenario produces the estimate.
0–3 = XS 4–6 = S 7–9 = M 10–12 = L 13 = XL
MAX() logic: After the requirements phase, all delivery teams work in parallel. Calendar duration equals the longest workstream — not the sum of all workstreams. This is why a project with six active teams does not take six times as long.

Important limitations
Scenario selection is the most impactful input. Choosing the wrong scenario can shift the estimate by 50% or more. If you are genuinely unsure, run two scenarios and present the range.
This tool does not account for project-specific constraints. Unusual source system architecture, regulatory requirements, team capacity issues, or concurrent project load are not captured here. Always validate L and XL estimates with the delivery teams.
The six delivery scenarios
Each scenario represents a distinct type of delivery work. The scenario is determined by where the data starts and where it needs to go.
S1 — New ingestion → Gold/Semantic
Files or APIs received from client. Ingestion pipelines land data and move it to Gold and/or Semantic (Redshift). Full pipeline build from scratch. Data Engineering is the dominant workstream.
S2 — Bronze → Silver → Gold
Data already in EDH Bronze. Work is transformation and layer movement only — no new source connections. DevOps effort is minimal.
S3 — Gold → Semantic (Redshift)
Curated Gold data modelled into agreed Semantic / Redshift structures. The Semantic / Modeler team leads; Data Engineering is supporting.
S4 — Redshift → Dashboards
Data already modelled in Redshift. Focus is BI build and validation only. No Data Engineering or DevOps work unless a new BI tool connection is needed.
S5 — Hybrid A (Light)
Some data exists in EDH, some is new. Limited reconciliation. Data Engineering and Semantic both involved, client dependency is moderate.
S6 — Hybrid B (Heavy)
Mix of existing EDH and new ingestion. Reconciliation, governance review, semantic alignment, and downstream impact analysis all required. Highest overall effort of the six scenarios.
Need a different scenario type?
The High-Level Estimator covers the six standard delivery scenarios. If your project is a platform migration, production break-fix, change request, multi-source consolidation, self-service enablement, DQ remediation, or API delivery — use the EDH Delivery Estimator, which covers 15 scenario types including all of these.
Understanding the output fields
Total calendar days
Days from kick-off to go-live. Includes waiting time (client responses, approval cycles) — not just build time.
Sprints
Calendar days ÷ 10, rounded up. One sprint = 10 calendar days (2 working weeks).
Internal person-days
Total effort from all internal teams combined. Used for capacity planning. Three teams spending 10 days each = 30 person-days, even if calendar duration is only 10 days.
Client person-days
Effort required from the client side — clarifications, UAT, data provision, approvals. This is the cost of the project to the client's own team.
Avg internal FTE
Internal person-days ÷ total calendar days. How many delivery team members are working in parallel on average. Use for sprint staffing decisions.
Scenario comparison table
Shows all six scenarios at the same size. Use to understand where your selected scenario sits relative to others at the same complexity level.
All-sizes table
Shows your selected scenario from XS to XL. Use to understand how the estimate changes if complexity is higher or lower than your current score suggests.
EDH data layers
Bronze
Raw data landing zone — ingested as received, no transformation applied.
Silver
Cleansed and standardised — data types normalised, nulls handled, basic rules applied.
Gold
Business-ready curated data — joins, aggregations, derived fields, full business logic.
Semantic / Redshift
Modelled structures in Amazon Redshift for analytics and reporting. What BI tools query directly.
Key terms
T-shirt size
Relative size label (XS to XL) assigned from the complexity score. Maps to pre-calibrated workstream day values per scenario.
Sprint
10 calendar days (2 working weeks). Standard time unit for planning and reporting.
MAX() logic
After requirements, delivery teams work in parallel. Calendar duration = the longest workstream, not the sum of all workstreams.
Client TAT
Client Turnaround Time — days for the client to respond to a clarification or approve a deliverable. Multiplied by cycle count = total waiting time added to the calendar estimate.
Complexity score
A numeric score from the Yes/No answers. Higher score = more complex = larger t-shirt size = more days.
